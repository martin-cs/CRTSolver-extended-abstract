****Review 3****
Q. Details are missing about the algorithm. The heuristics for checking candidate is not clearly explained.
Given a base solution modulo M, this heuristics considers adding multiples of M to the base solution as 
candidates. It's not clear how this is done. Does it add different multiples of M to each variables
(which would be exponential in the number of variables) or does it add the same multiple to each variable?
In any case, data about the effectiveness of this heuristic should be added to the experimental section.
A. DONE.

Q. The general approach looks suboptimal. For example, it looks inefficient to use an SMT solver to check 
candidates since this can be done by just evaluating polynomials at a point. Also, the description implies 
that new constraints are added to the "modulo solver" for each m_i. This also looks suboptimal, as each 
sub-problem (solving modulo m_i for some i) is independent of the others. It should then be enough to 
remember past candidates modulo M = m_1 ... m_{I-1} then
get a solution modulo m_i (with one call to the solver) and combine past candidates and new solution 
using the CRT.
A. For Martin to decide if we address this - and if so, how we address this.

Q. Another limitation is that there may be several solutions modulo each m_i but the algorithm does 
not use this fact.
A. For Martin to decide if we address this - and if so, how we address this.

Q. The experimental section is not very deep. The number of problems is not very large and all have a small 
number of variables and low degree polynomials, and the timeout is small (10s). It would be much more 
interesting to see how the approach scales to larger sizes of problems. Also, the paper does not explain 
how the problems were generated. The abstract says they are synthetic but that's not enough information. 
For techniques that rely on bit-blasting, it can be important to know the size of constants involved.
A. DONE. Outside scope.
